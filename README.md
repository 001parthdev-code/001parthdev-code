## Engineering Philosophy

### Build before you over-plan.

A system becomes understandable when it exists.

### Read implementations, not just documentation.

The fastest way to understand a system is often to trace how it actually works.

### Treat failures as engineering data.

A failed retrieval, unstable agent, slow pipeline, or broken abstraction tells you something about the architecture.

### Optimize for understanding.

I would rather understand a smaller system deeply than know the names of fifty frameworks.

### Build products, not demos.

A project becomes interesting when it has real constraints: users, scale, latency, reliability, security, or cost.

### Iterate aggressively.

Architecture is a hypothesis. Implementation and measurement decide whether it survives.
